## Authentication vs Authorization

<Summary>
Authentication checks **who you are** (email + password). Authorization checks **what you are allowed to do** (your role). Authentication always comes first. Not logged in → **401**. Logged in but not allowed → **403**.
</Summary>

</Callout>

<Summary>
Before OAuth, if a travel app needed your Gmail contacts, it asked for your Gmail **password**. That gave it full access to everything, and the only way to take it back was to change your password. OAuth fixed this with tokens that have limited permissions.

## Password hashing

<Summary>
I never store the password itself. I store an **Argon2 hash** of it. At login, I verify what the user typed against that hash. Argon2 is slow on purpose, so if the database leaks, attackers can't guess passwords fast, the way they can with MD5 or SHA-256.
</Summary>

**Why not MD5 or SHA-256?** They are built to be fast, so a GPU can try billions of guesses per second. Argon2 is built to be slow and to need a lot of memory for **every** guess.

**Salt:** Argon2 mixes a random value into each password before hashing, so two users with the same password get different hashes.

```js
const argon2 = require('argon2')

// REGISTER: hash and store (salt + settings are saved inside the hash string)
const hash = await argon2.hash(password)
await pool.query('INSERT INTO users (email, password) VALUES ($1, $2)', [email, hash])

// LOGIN: verify
const valid = await argon2.verify(user.password, password)
if (!valid) throw new AuthError('authentication failed')
```

## Passkeys (WebAuthn)

<Summary>
A passkey is a key pair on your device. The server keeps only the **public key**. At login the server sends a random challenge, the device signs it after Face ID, and the server checks the signature with the public key. No password is ever sent, so there's nothing to phish or leak.
</Summary>

## HTTP is stateless

<Summary>
HTTP doesn't remember anything between requests; every request arrives like a stranger. So after login, the client must send proof on **every** request: either a **session ID** (the server remembers the user) or a **JWT** (the token itself says who the user is).
</Summary>

- **Session (stateful):** the server saves you in Redis; the browser keeps only an ID.
- **JWT (stateless):** the token itself carries who you are.

## Session-based authentication

<Summary>
At login the server creates a random session ID, saves `sessionId → userId` in **Redis**, and sends the ID to the browser in a cookie. On every request the browser sends the cookie back and the server looks it up in Redis. Logout = delete the key, so access is gone instantly.
</Summary>

```js
// LOGIN (after verifying the password)
const sessionId = crypto.randomUUID()
await redis.setex(`session:${sessionId}`, 1800, JSON.stringify({ userId: user.id, role: user.role }))
res.cookie('sessionId', sessionId, { httpOnly: true, secure: true, sameSite: 'lax', maxAge: 1800000 })

// PROTECTED ROUTE
const data = await redis.get(`session:${req.cookies.sessionId}`)
if (!data) return res.status(401).json({ error: 'authentication failed' })

// LOGOUT: instant revocation
await redis.del(`session:${req.cookies.sessionId}`)
```

## JWT: JSON Web Tokens

<Summary>
A JWT is a signed token with three parts: header, payload, signature. The payload holds the user ID, role and expiry. The server checks the signature with its secret, with **no database lookup**, which is why it's called stateless. The payload is only encoded, not encrypted, so anyone can read it: never put secrets in it.
</Summary>

<JwtDecoder />

<JwtTamper />

`HEADER.PAYLOAD.SIGNATURE`

- **Header:** which algorithm signed it, e.g. `HS256`.
- **Payload:** `sub` (user ID), `role`, `exp` (expiry time).
- **Signature:** `HMAC-SHA256(header + "." + payload, SECRET)`. Change one letter of the payload and it no longer matches.

| Pros | Cons |
| --- | --- |
| No session storage | Hard to revoke before it expires |
| Works across many servers | A stolen token works until it expires |
| Great for microservices | Anyone can read the payload |
| Portable between services | Tokens can get large |

**Many services:** with HS256, every service needs the same secret to verify, so every service could also **create** tokens. With **RS256**, only the auth service has the private key to sign; the others only have the public key to verify.

```js
// LOGIN: create a JWT
const token = jwt.sign({ sub: user.id, role: user.role }, process.env.JWT_SECRET, { expiresIn: '15m' })

// MIDDLEWARE: verify on every protected request
function authenticate(req, res, next) {
  try {
    const token = req.headers.authorization.split(' ')[1] // "Bearer <token>"
    req.user = jwt.verify(token, process.env.JWT_SECRET)
  } catch {
    return res.status(401).json({ error: 'authentication failed' })
  }
  next()
}
```

<Callout type="trap">
The JWT payload is **encoded, not encrypted**. Anyone can decode it. Never put passwords or secrets in it: only the user ID, role and expiration.
</Callout>

<Summary>
With **sessions**, the server stores the state in Redis and the client only carries an ID, so it's easy to revoke but needs a lookup on every request. With **JWT**, the token carries the state, so there's no lookup and it scales easily, but you can't cancel it before it expires.
</Summary>

</Summary>

```js
async function refresh(token) {
  const record = JSON.parse(await redis.get(`rt:${token}`)) // { userId, role, familyId }
  if (!record || (await redis.exists(`revoked:${record.familyId}`))) throw new AuthError('invalid')

  // mark as used; NX fails if it was already used -> reuse detected
  const firstUse = await redis.set(`used:${token}`, 1, 'EX', THIRTY_DAYS, 'NX')
  if (!firstUse) {
    await redis.set(`revoked:${record.familyId}`, 1, 'EX', THIRTY_DAYS) // revoke whole family
    throw new AuthError('invalid')
  }

  const newToken = crypto.randomUUID()
  await redis.set(`rt:${newToken}`, JSON.stringify(record), 'EX', THIRTY_DAYS) // same familyId
  const accessToken = jwt.sign({ sub: record.userId, role: record.role }, SECRET, { expiresIn: '15m' })
  return { accessToken, refreshToken: newToken }
}
```

## Cookies

<Summary>
A cookie is not an auth method. It's a small piece of browser storage that is **sent automatically** with every request to that site. It can carry a session ID or a JWT. I protect it with **HttpOnly** (JavaScript can't read it), **Secure** (HTTPS only) and **SameSite** (not sent on cross-site requests).
</Summary>

<CookiePlayground />

A cookie can carry a session ID or a JWT. The mechanism is the session or the JWT; the cookie just carries it.

| Attribute | What it does |
| --- | --- |
| `HttpOnly` | JavaScript can't read it. Protects against XSS stealing the token. |
| `Secure` | Only sent over HTTPS. |
| `SameSite=Lax` | Not sent on cross-site POSTs or background requests; sent on normal link clicks. Reduces CSRF. |
| `SameSite=Strict` | Never sent on cross-site requests. Strictest CSRF protection. |
| `MaxAge` | How long the cookie lives. |

**Cookie vs Authorization header**

- **Cookie (browser apps):** sent automatically. HttpOnly protects against XSS, and SameSite against CSRF.
- **Authorization header (mobile, machine to machine):** `Authorization: Bearer eyJ…`, set manually. There's no CSRF risk because it's never sent automatically.

```js
res.cookie('sessionId', sessionId, {
  httpOnly: true, // JS can't read it
  secure: true, // HTTPS only
  sameSite: 'lax', // CSRF protection
  maxAge: 1800000, // 30 minutes
})
```

<Callout type="trap">
"What's the difference between a session and a cookie?" A session is the **authentication mechanism** (state on the server). A cookie is the **transport** (the browser stores and sends it). They're different layers.
</Callout>

</Summary>

## OAuth 1.0 and OAuth 2.0

<Summary>
OAuth lets an app use part of my data, like my Google contacts, **without my password**. Google asks me to approve, then gives the app a token with only that permission, and I can revoke it any time. OAuth 2.0 is only about **what the app can access**, not who I am; that part is OIDC.
</Summary>

**OAuth 1.0** solved delegation: the travel app redirects you to Google, you approve "read contacts," and the app gets a token for contacts only. You never gave your password, and you can revoke the token anytime. But it needed complex cryptographic signatures on every request.

**OAuth 2.0** simplified it with **bearer tokens** (no per-request signatures) and different flows:

| Flow | When to use |
| --- | --- |
| Authorization Code (+ PKCE) | Web, mobile and browser apps: the most common and most secure |
| Client Credentials | Machine to machine, no user involved |
| Device Code | TVs, CLIs, devices with no browser |
| Implicit | Old and deprecated; replaced by Authorization Code + PKCE |

| Component | What it is |
| --- | --- |
| Resource Owner | You, the user |
| Client | The app that wants access (travel app) |
| Resource Server | The server holding your data (Gmail) |
| Authorization Server | The server that issues tokens (Google auth) |

**Bearer token:** whoever *bears* (carries) the token gets access. The server doesn't check who is holding it, only that it's valid. That's why a stolen bearer token is dangerous.

<Callout type="trap">
OAuth 2.0 answers "what can this app access?", **not** "who is the user?" That gap is filled by OpenID Connect.
</Callout>

## PKCE

<Summary>
PKCE protects the login code. Before redirecting, the app makes a random secret (the **code_verifier**) and sends only its hash to Google. When it exchanges the code for tokens, it must send the original secret. So a stolen code alone is useless.
</Summary>

```js
async function apiKeyAuth(req, res, next) {
  const key = req.headers['x-api-key']
  if (!key) return res.status(401).json({ error: 'authentication failed' })

  // store and look up a HASH of the key, never the raw key
  const hash = crypto.createHash('sha256').update(key).digest('hex')
  const { rows } = await pool.query('SELECT user_id FROM api_keys WHERE key_hash = $1 AND active = true', [hash])
  if (!rows[0]) return res.status(401).json({ error: 'authentication failed' })

  req.user = { id: rows[0].user_id }
  next()
}
```

## RBAC: role-based access control

<Summary>
RBAC means each user has a **role** (user, moderator, admin) and each role has permissions. A middleware checks the role on every request and returns **403** if it's not allowed. Before that, authentication must return **401** for a bad token, not crash with 500.
</Summary>

<RbacSimulator />

- **user** → read own notes
- **moderator** → read and write any note
- **admin** → everything, plus the dead zone

```js
// authentication: who are you? (jwt.verify throws on a bad token, so catch it -> 401)
function authenticate(req, res, next) {
  try {
    const token = req.headers.authorization.split(' ')[1]
    req.user = jwt.verify(token, process.env.JWT_SECRET)
  } catch {
    return res.status(401).json({ error: 'authentication failed' })
  }
  next()
}

// authorization: what can you do?
function authorize(...roles) {
  return (req, res, next) => {
    if (!roles.includes(req.user.role)) return res.status(403).json({ error: 'forbidden' })
    next()
  }
}

app.get('/admin/dead-zone', authenticate, authorize('admin'), getDeadZoneNotes)
app.delete('/notes/:id', authenticate, authorize('admin', 'moderator'), deleteNote)
app.get('/notes', authenticate, authorize('user', 'moderator', 'admin'), getNotes)
```

**Specific messages tell attackers what to try next:**

- `user not found` → this email doesn't exist
- `incorrect password` → the email exists, now guess the password
- `account locked` → the email exists

Always return `401 { "error": "authentication failed" }`.

```js
app.post('/forgot', async (req, res) => {
  const user = await findUserByEmail(req.body.email)
  if (user) {
    const token = crypto.randomBytes(32).toString('base64url')
    await redis.set(`reset:${sha256(token)}`, user.id, 'EX', 900) // 15 min, stored hashed
    queue.add('send-reset-email', { to: user.email, token }) // in the background: no timing difference
  }
  res.json({ message: 'If an account exists, we sent a reset link.' }) // always the same
})

app.post('/reset', async (req, res) => {
  const key = `reset:${sha256(req.body.token)}`
  const userId = await redis.get(key)
  if (!userId) return res.status(400).json({ error: 'invalid or expired link' })

  await redis.del(key) // single use
  await pool.query('UPDATE users SET password = $1 WHERE id = $2', [await argon2.hash(req.body.password), userId])
  await revokeAllSessions(userId) // log out everywhere
  res.json({ message: 'Password updated. Please log in.' })
})
```

<Callout type="trap">
Sending the email *inside* the request makes "email exists" responses slower, which is a timing leak. Put the email on a background queue so both paths return equally fast.
</Callout>
