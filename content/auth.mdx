## Password hashing

<Summary>
Never store plain-text passwords. Store an Argon2 hash.
</Summary>

If the database is breached, plain-text passwords expose every user. A hash only gives the attacker a string they have to crack.

MD5 and SHA-256 are **fast**, so attackers can try billions of guesses per second. Argon2 is deliberately **slow and memory-hard**, which makes every guess expensive. It also adds a random salt to each password, so identical passwords produce different hashes.

```js
const argon2 = require('argon2')

// REGISTER: hash and store (salt + settings are saved inside the hash string)
const hash = await argon2.hash(password)
await pool.query('INSERT INTO users (email, password) VALUES ($1, $2)', [email, hash])

// LOGIN: verify
const valid = await argon2.verify(user.password, password)
if (!valid) throw new AuthError('authentication failed')
```

## HTTP is stateless

<Summary>
HTTP doesn't remember you. Every request needs to carry proof of identity.
</Summary>

Request 1, 2 and 3 each arrive with the server asking "who is this?" After login, something has to carry the proof. There are two solutions:

- **Session (stateful):** the server remembers you.
- **JWT (stateless):** the token carries the proof.

## Session-based authentication

<Summary>
The server stores the session in Redis. The browser holds only the session ID, in a cookie.
</Summary>

1. The user logs in with email + password, and the server verifies them.
2. The server creates a session ID `abc123` and stores `abc123 → { userId: 42 }` in Redis.
3. The session ID goes to the browser in a cookie.
4. On the next request, the browser sends the cookie automatically. The server looks up Redis and knows it's user 42.

```js
// LOGIN (after verifying the password)
const sessionId = crypto.randomUUID()
await redis.setex(`session:${sessionId}`, 1800, JSON.stringify({ userId: user.id, role: user.role }))
res.cookie('sessionId', sessionId, { httpOnly: true, secure: true, sameSite: 'lax', maxAge: 1800000 })

// PROTECTED ROUTE
const data = await redis.get(`session:${req.cookies.sessionId}`)
if (!data) return res.status(401).json({ error: 'authentication failed' })

// LOGOUT: instant revocation
await redis.del(`session:${req.cookies.sessionId}`)
```

**Stateful in distributed systems.** If the session is stored in one server's memory, a request that lands on another server fails. The fix is a **shared Redis** that every server reads from.

## JWT: JSON Web Tokens

<Summary>
The client carries a signed token with the claims inside. The server verifies the signature locally, with no lookup.
</Summary>

A JWT is `HEADER.PAYLOAD.SIGNATURE`, with each part base64url-encoded:

- **Header:** `{ "alg": "HS256", "typ": "JWT" }`
- **Payload:** `{ "sub": "42", "role": "user", "exp": 1799999999, "iat": 1700000000 }`
- **Signature:** `HMACSHA256(base64url(header) + "." + base64url(payload), SECRET_KEY)`

<Callout type="trap">
The JWT payload is **encoded, not encrypted**. Anyone can decode it. Never put passwords or secrets in it: only the user ID, role and expiration.
</Callout>

```js
// LOGIN: create a JWT
const token = jwt.sign({ sub: user.id, role: user.role }, process.env.JWT_SECRET, { expiresIn: '15m' })

// MIDDLEWARE: verify on every protected request
function authenticate(req, res, next) {
  try {
    const token = req.headers.authorization.split(' ')[1] // "Bearer <token>"
    req.user = jwt.verify(token, process.env.JWT_SECRET)
  } catch {
    return res.status(401).json({ error: 'authentication failed' })
  }
  next()
}
```

**Why is it called stateless?** A session needs a Redis lookup on every request. A JWT has the claims inside the token, so the server only checks the signature.

| Pros | Cons |
| --- | --- |
| No session storage needed | Hard to revoke immediately |
| Works across distributed servers | A stolen token is valid until it expires |
| Great for microservices | Payload is visible (not encrypted) |
| Portable between services | Tokens can grow large |

**Microservices: HS256 vs RS256.** With HS256, the same secret signs *and* verifies, so every service holds the signing secret, and one compromised service can create tokens. Prefer **RS256/ES256**: only the auth service signs, with a private key, and the other services verify with the public key.

- **Login:** the server issues an access JWT (15 min) and a refresh token (30 days, stored in Redis).
- **Normal request:** the server verifies the JWT locally, with no Redis. Fast.
- **JWT expired:** the client sends the refresh token → the server checks Redis → issues a new JWT and a **new** refresh token (rotation).
- **Logout:** revoke the refresh token. The access JWT still works for up to 15 minutes, which is an accepted trade-off.

**Reuse detection.** Every refresh token from one login belongs to a **family**. When a token is used, it's marked *used*, not deleted. If a used token shows up again, someone stole it, so the server revokes the **whole family**.


```js
async function refresh(token) {
  const record = JSON.parse(await redis.get(`rt:${token}`)) // { userId, role, familyId }
  if (!record || (await redis.exists(`revoked:${record.familyId}`))) throw new AuthError('invalid')

  // mark as used; NX fails if it was already used -> reuse detected
  const firstUse = await redis.set(`used:${token}`, 1, 'EX', THIRTY_DAYS, 'NX')
  if (!firstUse) {
    await redis.set(`revoked:${record.familyId}`, 1, 'EX', THIRTY_DAYS) // revoke whole family
    throw new AuthError('invalid')
  }

  const newToken = crypto.randomUUID()
  await redis.set(`rt:${newToken}`, JSON.stringify(record), 'EX', THIRTY_DAYS) // same familyId
  const accessToken = jwt.sign({ sub: record.userId, role: record.role }, SECRET, { expiresIn: '15m' })
  return { accessToken, refreshToken: newToken }
}
```

## Cookies

<Summary>
A cookie is not an authentication mechanism. It's a **transport**: browser storage plus automatic sending.
</Summary>

<CookiePlayground />

A cookie can carry a session ID or a JWT. The mechanism is the session or the JWT; the cookie just carries it.

| Attribute | What it does |
| --- | --- |
| `HttpOnly` | JavaScript can't read it. Protects against XSS stealing the token. |
| `Secure` | Only sent over HTTPS. |
| `SameSite=Lax` | Not sent on cross-site POSTs or background requests; sent on normal link clicks. Reduces CSRF. |
| `SameSite=Strict` | Never sent on cross-site requests. Strictest CSRF protection. |
| `MaxAge` | How long the cookie lives. |

```js
res.cookie('sessionId', sessionId, {
  httpOnly: true, // JS can't read it
  secure: true, // HTTPS only
  sameSite: 'lax', // CSRF protection
  maxAge: 1800000, // 30 minutes
})
```

**Cookie vs Authorization header**

- **Cookie (browser apps):** sent automatically. HttpOnly protects against XSS, and SameSite against CSRF.
- **Authorization header (mobile, machine to machine):** `Authorization: Bearer eyJ…`, set manually. There's no CSRF risk because it's never sent automatically.

<Callout type="trap">
"What's the difference between a session and a cookie?" A session is the **authentication mechanism** (state on the server). A cookie is the **transport** (the browser stores and sends it). They're different layers.
</Callout>

The server creates a random token per session and gives it to its own frontend. The frontend sends it back in a header on every state-changing request. evil.com can make the browser *send* requests, but the browser won't let it *read* notes.app's pages, so it can never learn the token.

`SameSite=Lax` already blocks this cross-site POST in modern browsers. CSRF tokens are the second layer. Also, never change state with GET.

```js
// at login: a random token tied to the session
req.session.csrfToken = crypto.randomBytes(32).toString('hex')

// frontend: send it back on every POST / PUT / PATCH / DELETE
fetch('/notes/7/delete', { method: 'POST', headers: { 'X-CSRF-Token': csrfToken } })

// middleware
function csrf(req, res, next) {
  if (['GET', 'HEAD', 'OPTIONS'].includes(req.method)) return next()
  if (req.get('X-CSRF-Token') !== req.session.csrfToken) {
    return res.status(403).json({ error: 'invalid csrf token' })
  }
  next()
}
```

<Callout type="trap">
CSRF only exists with **cookie** auth, because cookies are sent automatically. A token in the `Authorization` header is never attached automatically, so it can't be forged this way.
</Callout>

## OAuth 1.0 and OAuth 2.0

<Summary>
OAuth = tokens with specific permissions instead of passwords. OAuth 2.0 is **authorization only**.
</Summary>

**OAuth 1.0** solved delegation: the travel app redirects you to Google, you approve "read contacts," and the app gets a token for contacts only. You never gave your password, and you can revoke the token anytime. But it needed complex cryptographic signatures on every request.

**OAuth 2.0** simplified it with **bearer tokens** (no per-request signatures) and different flows:

| Flow | When to use |
| --- | --- |
| Authorization Code (+ PKCE) | Web, mobile and browser apps: the most common and most secure |
| Client Credentials | Machine to machine, no user involved |
| Device Code | TVs, CLIs, devices with no browser |
| Implicit | Old and deprecated; replaced by Authorization Code + PKCE |

| Component | What it is |
| --- | --- |
| Resource Owner | You, the user |
| Client | The app that wants access (travel app) |
| Resource Server | The server holding your data (Gmail) |
| Authorization Server | The server that issues tokens (Google auth) |

**Bearer token:** whoever *bears* (carries) the token gets access. The server doesn't check who is holding it, only that it's valid. That's why a stolen bearer token is dangerous.

<Callout type="trap">
OAuth 2.0 answers "what can this app access?", **not** "who is the user?" That gap is filled by OpenID Connect.
</Callout>

## API key authentication

<Summary>
A static secret key sent with every request. No login, no sessions, no JWTs. Used for machine-to-machine access.
</Summary>

The client sends `X-API-Key: sk_live_abc123xyz` (or `Authorization: Bearer …`), and the server looks the key up: `sk_live_abc123xyz → user 42, permissions: read`.

```js
async function apiKeyAuth(req, res, next) {
  const key = req.headers['x-api-key']
  if (!key) return res.status(401).json({ error: 'authentication failed' })

  // store and look up a HASH of the key, never the raw key
  const hash = crypto.createHash('sha256').update(key).digest('hex')
  const { rows } = await pool.query('SELECT user_id FROM api_keys WHERE key_hash = $1 AND active = true', [hash])
  if (!rows[0]) return res.status(401).json({ error: 'authentication failed' })

  req.user = { id: rows[0].user_id }
  next()
}
```

| Use case | Best auth | Why |
| --- | --- | --- |
| Web app login | Session or JWT | User identity needed |
| Mobile app | JWT | Stateless, portable |
| Machine to machine | API key | No user involved |
| Third-party access | OAuth 2.0 | Delegated permissions |
| Sign in with Google | OIDC | Identity from the provider |

## RBAC: role-based access control

<Summary>
Users get roles, and roles get permissions. The server checks the role on every request and returns 403 if it's not allowed.
</Summary>

<RbacSimulator />

- **user** → read own notes
- **moderator** → read and write any note
- **admin** → read, write, delete, and access the dead zone

```js
// authentication: who are you? (jwt.verify throws on a bad token, so catch it -> 401)
function authenticate(req, res, next) {
  try {
    const token = req.headers.authorization.split(' ')[1]
    req.user = jwt.verify(token, process.env.JWT_SECRET)
  } catch {
    return res.status(401).json({ error: 'authentication failed' })
  }
  next()
}

// authorization: what can you do?
function authorize(...roles) {
  return (req, res, next) => {
    if (!roles.includes(req.user.role)) return res.status(403).json({ error: 'forbidden' })
    next()
  }
}

app.get('/admin/dead-zone', authenticate, authorize('admin'), getDeadZoneNotes)
app.delete('/notes/:id', authenticate, authorize('admin', 'moderator'), deleteNote)
app.get('/notes', authenticate, authorize('user', 'moderator', 'admin'), getNotes)
```

**Generic errors.** Messages like "user not found," "incorrect password" or "account locked" tell attackers which emails exist. Always return `401 { error: 'authentication failed' }`.

**Timing attacks.** If the email doesn't exist, login fails fast (~5 ms). If the email exists but the password is wrong, hashing makes it slow (~200 ms). The attacker measures the difference.

```js
  const key = `reset:${sha256(req.body.token)}`
  const userId = await redis.get(key)
  if (!userId) return res.status(400).json({ error: 'invalid or expired link' })

  await redis.del(key) // single use
  await pool.query('UPDATE users SET password = $1 WHERE id = $2', [await argon2.hash(req.body.password), userId])
  await revokeAllSessions(userId) // log out everywhere
  res.json({ message: 'Password updated. Please log in.' })
})
```

<Callout type="trap">
Sending the email *inside* the request makes "email exists" responses slower, which is a timing leak. Put the email on a background queue so both paths return equally fast.
</Callout>
