## What is a backend?

<Summary>
The backend is the central server that **stores data for everyone**, keeps secrets like the database password, and applies the same rules to every user. The frontend runs on the user's own device and forgets everything when the tab closes.
</Summary>

## Glossary

<Summary>
JavaScript is just the language. **V8** is the engine that runs it. The **browser** and **Node.js** are runtimes: V8 plus extra tools (DOM and fetch in the browser; files and networking in Node). **Express** is a framework on top of Node for routes and middleware.
</Summary>

| Term | Meaning |
| --- | --- |
| HTTP / HTTPS | Client sends a request, server sends a response. HTTPS is the same protocol, encrypted in transit. |
| WebSockets | One connection stays open, and both sides can send messages at any time. Chat, live dashboards, games. |
| Runtime environment | What gives JavaScript memory, an event loop, and APIs to talk to the outside world. |
| Browser | Frontend runtime: V8 + browser APIs (`DOM`, `window`, `fetch`). |
| Node.js | Backend runtime: V8 + Node APIs (file system, networking, processes). |
| V8 / libuv | V8 runs your JavaScript. libuv handles async I/O with the OS and tells Node when work is done. |
| Event loop | Keeps asking "is something ready to run?" and runs the matching callback. |
| Callback | A function you pass to another function, to be called later when something is ready. |
| Express | Node web framework: routing, middleware, request/response handling. |
| Ports | 80 = HTTP, 443 = HTTPS (used silently). Any other port must be typed: `localhost:3000`. |

## How a request travels

<Summary>
When I type google.com: **DNS** gives the IP → the browser connects on port 443 → **Nginx** decrypts HTTPS and forwards plain HTTP to **Node** on port 3000 → Node runs my code and queries the **database** → the response goes back the same way, Nginx encrypts it, and the browser shows the page.
</Summary>

**Why not let users hit Node directly?**

- Nginx handles the SSL certificate, so Node never deals with HTTPS.
- Only ports 80 and 443 are open to the internet. Port 3000 stays private.
- One Nginx can send traffic to many app servers, and skip one that's down.

```nginx
upstream app {
  server 10.0.0.11:3000;
  server 10.0.0.12:3000;
  server 10.0.0.13:3000;
}

server {
  listen 443 ssl;
  server_name yourapp.com;
  ssl_certificate     /etc/letsencrypt/live/yourapp.com/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/yourapp.com/privkey.pem;

  location / {
    proxy_pass http://app; # plain HTTP to Node
  }
}
```

## SSH vs SSL

<Summary>
**SSL** (today really TLS) encrypts the traffic between the browser and my server, which turns HTTP into HTTPS; Nginx handles it. **SSH** is a completely different tool: it lets me log into my server's terminal from my laptop.
</Summary>

| | SSL / TLS | SSH |
| --- | --- | --- |
| What | Certificate that encrypts browser ↔ server traffic | Remote terminal access to your server |
| Who handles it | Nginx (your Node app never touches it) | You, the developer |
| Command | `sudo certbot --nginx -d yourapp.com` | `ssh ubuntu@yourserverIP` |

SSL/TLS is the envelope; HTTPS is HTTP delivered inside that sealed envelope.

</Summary>

## CORS and the preflight request

<Summary>
CORS is a **browser** rule: JavaScript on one site can't read a response from another site unless that server allows it with `Access-Control-Allow-Origin`. The browser enforces it; the backend decides. For requests like DELETE, or ones with an Authorization header, the browser first sends an **OPTIONS preflight** to ask permission.
</Summary>

- **Who decides?** The backend, with `Access-Control-Allow-*` headers.
- **Backend → database?** No browser involved, so there's no CORS there.

A **preflight** (`OPTIONS`) happens for `PUT`/`DELETE`, custom headers, an `Authorization` header, or a `Content-Type: application/json` body.

```js
const cors = require('cors')

app.use(cors()) // development: allow any origin
app.use(cors({ origin: 'https://yourapp.com' })) // production: only your frontend
```

<Callout type="trap">
"CORS protects my API from other servers." No. CORS is enforced only by **browsers**. `curl` or another backend can call your API freely. Real protection is authentication.
</Callout>

## Core principles: client-server and stateless

<Summary>
Every HTTP request is **independent** and carries everything the server needs, like the Authorization header. The server doesn't remember earlier requests. That's why any server behind a load balancer can handle any request, and I can scale by just adding servers.
</Summary>

</Summary>

## Anatomy of an HTTP message

<Summary>
Every HTTP message has four parts: the **first line** (method + URL, or status code), **headers**, a **blank line**, and an optional **body**.
</Summary>

| Part | What it's for |
| --- | --- |
| Start line | Request: method + URL + version. Response: version + status code + text. |
| Headers | Extra information about the request or response. |
| Blank line | Separates headers from the body. |
| Body (optional) | The data: sent in POST/PUT/PATCH, returned in responses. A GET normally has no body. |

```http
GET /api/users HTTP/1.1
Host: api.shop.com
User-Agent: Mozilla/5.0 (...)
Accept: application/json
Authorization: Bearer abc123token
Connection: keep-alive
```

```http
HTTP/1.1 200 OK
Date: Wed, 27 Aug 2025 10:30:00 GMT
Content-Type: application/json
Content-Length: 187
Cache-Control: no-cache

{ "status": "success", "data": [ ... ] }
```

## Important headers

<Summary>
Headers are extra information about the request or response: the body format (`Content-Type`), who I am (`Authorization`), cookies, caching rules, compression, and security rules like HSTS and CSP.
</Summary>

| Header | Sent in | What it does | Example |
| --- | --- | --- | --- |
| Content-Type | Both | Media format of the body | `application/json` |
| Authorization | Request | Auth credentials | `Bearer eyJhbGci…` |
| Accept | Request | Response format the client wants | `application/json` |
| Cookie | Request | Cookies stored in the browser | `sessionId=xyz789` |
| Set-Cookie | Response | Create/update a cookie | `sessionId=xyz789; HttpOnly` |
| Cache-Control | Both | How the response may be cached | `max-age=3600, public` |
| Content-Encoding | Response | Compression used on the body | `gzip` |
| Content-Length | Both | Body size in bytes | `1024` |
| User-Agent | Request | Info about the client | `Mozilla/5.0 (…)` |
| Strict-Transport-Security | Response | Always use HTTPS | `max-age=31536000` |
| Content-Security-Policy | Response | Which resources may load | `default-src 'self'` |
| X-Content-Type-Options | Response | Don't guess the content type | `nosniff` |
| Referrer-Policy | Response | How much referrer info is sent | `strict-origin-when-cross-origin` |

<Summary>
Idempotent means sending the same request twice leaves the **same final result** as sending it once. GET, PUT and DELETE are idempotent; POST is not, so retrying it can create a **duplicate order**. It matters because networks fail and clients retry.
</Summary>

## Status codes

<Summary>
**2xx** success, **3xx** go elsewhere or use your cache, **4xx** the client made a mistake, **5xx** the server failed. The common ones: 200, 201, 204, 301, 304, 400, 401, 403, 404, 409, 429, 500, 502, 503, 504.
</Summary>

| Range | Meaning | Codes |
| --- | --- | --- |
| 1xx | Information | 100 Continue (keep sending the body) |
| 2xx | Success | 200 OK · 201 Created · 204 No Content |
| 3xx | Redirect / cache | 301 Moved permanently · 302 Temporarily elsewhere · 304 Not Modified (use your cache) |
| 4xx | Client problem | 400 Bad request · 401 Not authenticated · 403 Not allowed · 404 Not found · 405 Wrong method · 409 Conflict · 429 Too many requests |
| 5xx | Server problem | 500 Unexpected error · 501 Not implemented · 502 Bad upstream response · 503 Unavailable · 504 Upstream timeout |

<Callout type="trap">
502 vs 504: both come from a proxy like Nginx. **502** = the upstream (Node) sent a bad response or refused the connection (e.g. the app crashed). **504** = the upstream didn't answer in time.
</Callout>
